# Deploying Hathorn Dashboard

A permanent address that survives restarts, weekends and me. Roughly ten minutes
of clicking, once.

Everything the platform needs is declared in `render.yaml`, so the host builds
itself. What you cannot delegate is the account and the card — the rest is done.

---

## Why Render rather than Vercel

Vercel is the obvious home for a Next.js app, and it is the wrong one here for a
specific reason: **this app writes to disk.** Uploaded documents live under
`DATA_DIR/documents`, verified backups under `BACKUP_DIR`, and a serverless
filesystem loses both between requests. The background job queue also wants a
process that stays running rather than one that wakes per request.

Render gives a persistent disk, an always-on process and scheduled jobs in the
same blueprint. Fly.io would do equally well; Vercel would mean giving up
document upload and moving backups to object storage first.

## What you do

**1. Create the account.** [render.com](https://render.com) → sign up with the
GitHub account that owns this repository.

**2. Deploy the blueprint.** New → **Blueprint** → choose this repository →
Render reads `render.yaml` and shows a web service, a Postgres database and two
scheduled jobs. Approve it.

Expect roughly $7/month for the service, $6 for the smallest database, and a few
dollars for the scheduled jobs. The free tiers exist but sleep after fifteen
minutes and expire the database after thirty days, which recreates the problem
this is meant to solve.

**3. Set one variable.** After the first deploy Render issues an address like
`hathorn-dashboard.onrender.com`. Put it in `NEXT_PUBLIC_BASE_URL` on the web
service. Emailed links and the QuickBooks redirect are built from it, so it must
be the address people actually use — set it to the custom domain if you attach
one.

**4. Create the schema.** Once, from Render's shell on the web service. This
applies the schema and every migration to the live database, then verifies it:

```bash
DATABASE_MIGRATOR_URL="$DATABASE_URL" npx tsx scripts/migrate-to-postgres.ts
npm run db:verify
```

`db:verify` recomputes financial totals and compares them, rather than only
counting rows. A type coercion that turns 114.2 into 114 passes a row count and
fails a client.

**5. Create the first real user.** The demo seed refuses to run against
`APP_ENV=PRODUCTION` under any configuration, which is deliberate — it wipes the
book and installs known passwords. Create the first admin from the Render shell:

```bash
npm run create-admin -- "you@hathornadvisorygroup.com" "Your Name"
```

It prints a one-time password and requires a change at first sign-in.

**6. Enrol two-factor.** Staff MFA is required whenever `APP_ENV=PRODUCTION`, so
the first sign-in walks you into enrolment. Keep the backup codes.

## Before you point a real client at it

Run the preflight against the live environment — Render shell, on the web
service:

```bash
npm run preflight
```

It refuses configurations that would come up wrong: a signing key still at its
published default, backups landing on the same disk as the database, a base URL
pointing at localhost, or a demo flag left switched on. It exits non-zero when
something would break, so it can gate a deploy.

Then, in order:

1. **Attach the custom domain** — `app.hathornadvisorygroup.com` or similar.
   Render issues the certificate. Update `NEXT_PUBLIC_BASE_URL` to match.
2. **Confirm the scheduled jobs ran.** `hathorn-jobs` every five minutes and
   `hathorn-backup` nightly. Without the first the queue never drains; without
   the second there are no backups. Both are visible in the Render dashboard.
3. **Prove a restore.** `npm run restore:drill` writes evidence to
   `docs/RESTORE-DRILL-LOG.md`. A backup that has never been restored is a
   rumour.
4. **Run one real close end to end** before a client sees anything.

## What each secret does, and what happens without it

| Variable | Required | Without it |
|---|---|---|
| `AUTH_SECRET` | yes | The app refuses to start. Generated by Render. |
| `ENCRYPTION_KEY` | yes in production | The app refuses to start. Must differ from `AUTH_SECRET`. |
| `NEXT_PUBLIC_BASE_URL` | yes | The app refuses to start. Emailed links and OAuth redirects come from it. |
| `BACKUP_DIR` | yes in production | The app refuses to start rather than write backups beside the live data. |
| `DATABASE_URL` | yes here | Falls back to SQLite on the local disk. |
| `RESEND_API_KEY` | no | Publish notifications and password resets become silent no-ops. |
| `ANTHROPIC_API_KEY` | no | Story drafting and the copilot fall back to deterministic output. |
| `QBO_CLIENT_ID` / `QBO_CLIENT_SECRET` | no | The bookkeeper uploads four CSVs a month, which is the supported path today. |

**Never set on a client-facing host:** `LEDGER_ALLOW_LOCAL_PROD`,
`REQUIRE_STAFF_MFA=0`, `ALLOW_DEMO_SEED`, `ENABLE_MOCK_INTEGRATION`. Preflight
fails on each of them.

---

## Rotating keys later

`ENCRYPTION_KEY` protects QuickBooks refresh tokens and MFA secrets. To rotate
it, set the old value as `ENCRYPTION_KEY_PREVIOUS` and the new one as
`ENCRYPTION_KEY`. Existing ciphertext keeps decrypting and is re-encrypted on
next write. Remove the previous key once a full cycle has passed.

Rotating `AUTH_SECRET` signs everyone out immediately. That is the correct
response to a suspected leak and a bad surprise otherwise.

## If you would rather use Fly.io

The shapes match: a Machine with a mounted volume at `/var/data`, a Postgres
cluster, and two scheduled machines running `npm run jobs:tick` and
`npm run backup`. The environment variables above are identical. Fly needs a
Dockerfile, which this repository does not carry yet — ask and it takes a few
minutes.
